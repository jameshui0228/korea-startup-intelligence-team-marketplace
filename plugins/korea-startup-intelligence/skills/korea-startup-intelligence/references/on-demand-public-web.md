# API 키 없는 수동 공개 웹 조사

## 제품 경계

허구김의 기본 모드는 `on_demand`다. 사용자가 플러그인을 호출한 현재 작업에서만 조사하며,
예약 작업·heartbeat·cron·백그라운드 프로세스·앱 종료 후 실행을 요구하거나 생성하지 않는다.
핵심 기능에는 네이버·YouTube·KOSIS·별도 LLM API 키가 필요하지 않다. 키 기반 connector는 사용자가
나중에 명시적으로 원할 때만 선택 사항이다.

API 키가 없을 때 Codex의 공개 웹 검색·브라우징으로 접근 가능한 원문을 읽는다. 로그인·유료벽·비공개 계정·robots·접근 제한을
우회하지 않는다. 검색 결과 조각은 원문 검토가 아니며, 공개 웹 표본은 플랫폼 전체나 한국 인구를 대표하지 않는다.

## 한 번의 요청으로 처리하는 흐름

1. `signal web-plan --topic "고객 문제" --limit 12` 또는 `blue-ocean run --topic "고객 문제"`로
   공개 SNS·채용·특허·표준·논문·기술 가격·조달·앱·커머스·펀딩·규제·공식 통계 조사 계획을 만든다.
2. Codex가 최대 6개 검색 묶음과 10개 원문을 우선 처리한다. 더 필요한 계열은 같은 사용자 요청 안에서 다음 묶음으로 이어가되,
   읽지 않은 원문을 읽었다고 표시하지 않는다.
3. 실제로 읽은 원문만 `signal template` 계약에 맞춰 배열로 만들고
   `signal batch-import --file REVIEWED_SIGNALS.json`으로 한 번에 접수한다. 한 항목이라도 유효하지 않으면 관측은 전부 저장하지 않는다.
4. 접수 직후 관련 후보 재검토 대기열과 포트폴리오 평가를 갱신한다. 그 뒤 `blue-ocean run --no-refresh` 또는
   `blue-ocean reassess --apply`로 판단 변화와 다음 행동을 연결한다.
5. 새 후보는 dossier와 같은 근거 ID를 연결해 저장한다. 실험 결과가 없으면 `blue-ocean bootstrap`으로 공개자료·대안·채널·
   단위경제 가정·첫 검증 기준까지만 진행한다.

## 계열별 증거 한계

- 공개 SNS·커뮤니티: 실제 이용자 역할이 원문에서 확인된 경우만 `speaker_role=customer`; 언급량은 구매가 아니다.
- 채용: 원 고용주 공고의 업무·요구 기술을 확인한다. 공고는 채용 완료나 고객 주문이 아니다.
- 특허·표준·논문: 출원/등록, 초안/시행, 등록일/발행일을 구분한다. 기술 공급은 수요와 별도다.
- 기술 가격·커머스·앱: 같은 제품·옵션·단위·지역·기간을 비교한다. 검색 결과 수와 리뷰 수는 판매량이 아니다.
- 조달: 사전규격·입찰·낙찰·계약을 구분한다. 한 발주기관을 시장 전체로 일반화하지 않는다.
- 크라우드펀딩: 후원·프리오더·결제·배송·환불 상태를 분리한다. 달성액은 반복 매출이 아니다.
- 규제: 예고·공포·시행일과 적용 대상을 공식 원문에서 확인한다. 법률 자문이 아니다.
- KOSIS·ECOS: 정의·단위·모집단·기준 기간·정규화·공표 판본을 기록한다. 검색 조각을 수치 근거로 저장하지 않는다.

## 사용자에게 보여 줄 결과

내부 JSON 대신 다음을 우선 보여 준다: 이번에 실제 읽은 범위, 새 변화, 고객 문제, 현재 대안/지출,
공급 공백 가설, 한국 조건, 가장 강한 반례, 아직 모르는 점, 지금 할 행동 하나와 통과/중단 기준.
새 근거가 약하면 아이디어 수를 채우지 않는다. “API 키가 없다”는 이유만으로 조사를 중단하지 않지만,
웹 접근이 없거나 원문이 막히면 최신 확인을 완료했다고 주장하지 않는다.
