# gstack에서 가져온 창업 의사결정 방식

아이디어를 사업 가설로 좁히거나 기존 제안을 반대 관점에서 개선할 때 사용한다.
출처는 [garrytan/gstack의 검토한 버전](https://github.com/garrytan/gstack/tree/a6b3a57512ca6d5c6aa5b68f74f736195021f96e)이며,
읽은 파일·범위·구현 대응은 플러그인 루트 assets/gstack-study.json에 기록했다.
원 저장소는 소프트웨어 개발 중심이므로 그 도구·명령·말투를 그대로 실행하지 않고 한국 전 분야 창업에 맞춰 적용한다.

## 1. 시장 탐색은 넓게, 고객 문제는 구체적으로

office-hours와 plan-ceo-review의 문제 재정의 방식을 다음처럼 사용한다.

- 기존 지식으로 예상한 설명, 이번에 읽은 최신 자료, 그 둘을 바탕으로 한 독자적 가설을 구분한다.
- “트렌드여서 뜬다” 대신 누가 어떤 상황에서 무엇을 해결하지 못하는지 쓴다. 고객 이름/연락처를 요구하지 말고 역할·행동·결과로 특정한다.
- 직접 경쟁 제품뿐 아니라 카카오톡·엑셀·외주·지인·기존 직원·아무것도 하지 않기의 비용을 비교한다.
- 주류 설명과 다른 가설이 실제 근거로 성립하면 제안한다. 독창적으로 보이려고 억지로 반대하지 않는다.
- 영업 비밀·개인 자료를 검색어로 보내지 않는다. 공개 카테고리/문제/대체재로 조사한다.

## 2. 단계에 맞는 고객 진단

`venture-review prepare --dossier-id dossier-ID --stage STAGE`는 질문 우선순위를 바꾼다.
단계가 확인되지 않았으면 unknown. 단계 입력은 창업자의 설명이지 실제 매출 인증이 아니다.

| 단계 | 우선 확인할 것 |
|---|---|
| pre_product | 행동으로 나타난 수요, 현재 해결 방식, 가장 구체적인 고객 |
| users | 현재 사용 방식, 가장 작은 유료 가치, 관찰 중 예상 밖 행동 |
| paying | 반복 구매되는 핵심 가치, 사용의 놀라운 점, 미래에 필요해질/사라질 조건 |
| unknown | 여섯 질문의 미확인 상태를 유지하고 중요한 것부터 확인 |

현재 유효한 답은 반복 질문하지 않는다. 근거/조사가 바뀌면 답을 재검토하되 이전 보류·기각 결정을 몰래 지우지 않는다.
가입·설문·호감도도 제한된 정보지만, 결제·재사용·실제 손실과 같은 증거라고 취급하지 않는다.
사용 관찰이 없으면 없다고 적는다. 사용자를 불편하게 만들기 위한 추궁이나 과도한 확신은 채택하지 않는다.

## 3. 대안에서 작은 실행으로

현재 방식 유지, 최소 서비스, 확장 제품 중 실제로 구별되는 대안을 비교한다. 최소안을 항상 정답으로 삼지는 않는다.
선택 이유에는 고객 가치, 자본·시간·공급 제약, 전환 비용, 첫 고객에게 닿는 경로, 중단 조건을 넣는다.
개발 전에 “아무것도 만들지 않는 수동 서비스로 무엇을 배울 수 있나”를 점검한다.
허가·안전·시설·제조가 핵심인 산업에 소프트웨어의 빠른 출시 관행을 그대로 강요하지 않는다.

제품/서비스 설계에서는 첫 접점→이용→결제/재이용과 함께 무응답·공급 부족·오류·취소·문의 상황을 확인한다.
이는 plan-design-review의 사용자 여정·상태 점검을 확장한 조사 절차다. 실제 화면/고객을 관찰했다고 말하지 않는다.
현재 요청이 단순 시장 조사이면 UI 설계·시제품 개발·광범위한 심사 절차를 끼워 넣지 않는다.

## 4. 주장, 산출물, 검증을 연결

spec·plan-eng-review·review·QA에서 참고한 원칙은 다음 실행기로 이어진다.

- 실험: `validation plan`에 측정·분모·기간·통과/중단 기준을 먼저 등록하고 `validation result`에 실제 관측만 넣는다.
- 지원서: `application`에서 본문→원문 근거→공식 평가항목→예산/일정→발표/Q&A를 연결한다. 문장 유창함은 시장 검증이 아니다.
- 반대 검토: 완전성·일관성·명확성·범위·실행 가능성의 실제 결함을 찾고 수정한 산출물을 다시 확인한다.
  같은 모델의 재검토는 독립 전문가 합의가 아니다. 주관적 문서 점수를 선정 확률로 변환하지 않는다.
- 기능 수정: 정상 사례뿐 아니라 자료 만료, 잘못된 단위, 미지수, 중단/재개, 기존 기록 보존을 테스트한다.
  구조 테스트 통과와 실제 서비스 연결·고객 결과 검증을 분리한다.

## 5. 실패를 잊지 않는 누적

retro·learn의 이력/모순 점검은 research-work start/complete/history와 기존 revision/feedback에 적용한다.
조사했다/근거를 찾지 못했다/접근할 수 없었다를 나누고, 범위와 다음 행동을 남긴다. “검색 결과 없음”은 경쟁자 부재가 아니다.
동일 근거를 다시 가져온 일을 새로운 발견으로 세지 않는다. 새로운 내용·결정 또는 재검토 시점이 있어야 후속 조사로 돌아간다.
성공뿐 아니라 중단·실패·미실행·보류도 분모에 남긴다. 기간·표본·관측 정의가 다르면 전후 개선 수치를 내지 않는다.
한 사례에서 얻은 교훈은 적용 조건과 반례를 유지한다. 코드/규칙 자동 교체나 실패 기록 삭제로 자기 개선을 가장하지 않는다.

## 채택하지 않은 것

gstack의 자동 설치·업그레이드·훅·쿠키 가져오기·원격 분석 수집·별도 모델 실행·자동 에이전트 위임은 켜지 않았다.
모델 가중치 훈련, 전체 저장소 실행 검증, YC 추천, 생산성 배수, 선정·수상 보장은 주장하지 않는다.
기본 경로는 추가 API 키 없이 현재 Codex와 허용된 공개 자료/사용자 자료로 수행한다.
